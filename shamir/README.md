# shamir — 点击即用的文件分片工具

> 任意文件进 → n 个分片 + 1 个密文出。凑齐任意 k 个分片 → 原文件回来。
> 纯前端、零后端、零外发请求。端点：https://tdstud1o.github.io/tool/shamir/
>
> 产物：密文 `<stem>.tscf`（TSCF 容器）+ 分片 `<stem>_shareN.txt`。
> **v0.2 破坏性更名**：容器头 SMCF/SMPK → **TSCF/TSPK**，扩展名 `.tsss` → **`.tscf`**；旧密文不再兼容（此前无外部用户）。

背景与生态位调研见博客：找遍了全网的 shamir 方案，没有我要的"点击即用"的版本（2026-10-17）。

## 验收标准

- 任意文件（照片/文档/存档/压缩包），不限格式
- 混合加密：随机 key 做 AES-256-GCM 加密文件；Shamir 只分片这个 key
- 返回物：n 个分片（每片几十字节文本）+ 1 个密文（压缩后通常远小于原文件）
- 恢复：任意 k 个分片 + 密文 → 原文件，校验失败明确报错
- 全程浏览器本地计算，GitHub Pages 静态部署

## 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 分片引擎 | **自实现 secp256k1 基域 GF(p) 上的 Shamir**（BigInt，零依赖） | p = 2²⁵⁶−2³²−977，32 字节密钥天然 < p，**不需要取模归约**（归约不是单射，会让两个密钥塌成同一个值）；x 不再被单字节坐标限制，n 上限 16,777,215；无查表、无运行时表 |
| 加密 | **Web Crypto API · AES-256-GCM** | 浏览器原生，无需引入库；key 32B 随机生成，IV 12B，AEAD 自带完整性 |
| 构建 | **Vite + TypeScript + vite-plugin-singlefile** | TS 类型安全；打包为**单个自包含 HTML**——可整页另存离线使用、可人工审计、无 CDN 运行时依赖 |
| UI | **无框架 vanilla TS + 手写 CSS** | 工具只有"拆分/恢复"两个动作，上框架是负资产；深色简洁风 |
| 分片载体 | 文本格式（带头校验），支持复制/下载/打印 | `TSK1:x:组1,组2,…` 结构（TSK = TD Shamir Key，1 为格式版本），每组只有 32B 的 y（k 可选），坐标 x 只写一次，几行字符，二维码/纸面均可承载 |
| 部署 | **GitHub Actions → actions/deploy-pages** | Pages 固定 URL 为 `tdstud1o.github.io/tool/`，Vite `base=/tool/shamir/` |

### 明确不选

- **React/Vue 等框架**：两个表单不需要组件体系，徒增体积与审计成本
- **运行时 CDN 引用**：隐私工具必须整页自包含，断网可用
- **后端 / 对象存储**：k-of-n 本来就只要求凑 k 片，云端存储反而扩大攻击面
- **SLIP-39/助记词生态**：本工具面向文件，不做 BIP39 兼容

## 数据格式（v1 草案）

两层同款 TLV 容器（PNG/age 风格，支持向前扩展）：

```
TLV 通用结构：magic(4B) + version(1B) + tag(1B) + len(4B 大端) + value 序列
兼容规则：解析器必须跳过未知 tag；约定 lastTag 的块必须放最后；单值上限 4 GiB
```

**内层 TSPK 载荷包**（先打包、再整体加密——元数据、存证、签名、链指针全部藏进密文）：

```
TSPK v1：
  0x01 FILENAME    utf-8 原文件名
  0x04 CREATED_AT  u64 毫秒（原文件创建/拆分时间，属于元数据，不外露）
  0x05 MIME        utf-8
  0x06 NOTE        utf-8 备注
  0x07 SHA256      原始 DATA 的 SHA-256（32B）
  0x12 OTS_RECEIPT OpenTimestamps .ots 回执原文（用户勾选才提交哈希）
  0x11 DATA        原始数据（无 NEXT 时的最后一个块）
  0x13 NEXT        下一层的完整 TSCF 字节（末块；缺失 = 这是最后一层）
```

**明文侧（不凑齐分片也能看到的全部内容）——TSCF 密文容器**：

```
TSCF | v1
  0x02 K            4B   分片阈值（u32 大端；必需，与该层分片交叉校验）
  0x03 N            4B   分片总数（u32 大端；**仅单层密文写入**，多层链一律不写）
  0x04 IV           12B  AES-GCM nonce
  0x05 CIPHERTEXT   ...  AES-256-GCM(key, TSPK 包)
  0x06 STYLE        1B   外观编号（可选，缺失 = 0x00 默认；只写最外层）
```

链指针放在**内层**：`0x13 NEXT` 跟着载荷一起被加密。放外层的话，拿到 `.tscf` 的人不用
密钥就能顺着块头数出层数、逐层量出各层大小——"一共几层"本身就是元数据。
放进内层后，明文侧只剩「这一层要几片」和 12B 随机 IV，别的一概看不见。
代价是必须解开当前层才知道有没有下一层，而恢复本来就是逐层进行的，所以这个代价为零。

`0x03 N` 只在**单层**密文里出现。多层链不写它：那会把"这套一共多少片"这种全局信息
在每一层重复一遍，多占字节，也和"每层只暴露自己 k"的设想相悖。
代价是恢复端在多层密文上**无从得知总片数**——它只能看到你实际导入了多少片，
所以"这一层 k 超过了总片数"这种判断只对单层密文成立，多层密文一律只说"还差 x 片"。

明文侧刻意只有「参数 + 12B 随机 IV + 密文」：没有文件名、没有大小提示、没有压缩算法。（0x01 这个编号是早期草稿留下的，在 TSCF 里从未启用，解析时按未知 tag 跳过。）

### 外观（style）：密文长什么样

`0x06 STYLE` 是唯一一处**故意**放在明文侧的表现层信息：拿到 `.tscf` 的人先看到什么形状，
本来就得能读到，否则恢复端无从渲染。它不参与加密，也不影响能不能解开——
旧版恢复端读到不认识的编号，按默认外观呈现，分片照样能解。

| 编号 | 名称 | 拆分端 | 恢复端 |
| --- | --- | --- | --- |
| 0x00 | 普通 | 任意文件，多层 | 普通文件卡（图片自动预览） |
| 0x01 | 碎片 | **只收图片**，最多 6 层 | 6 块拼满舞台的碎玻璃：解锁一层点亮一块，每块装的内容互不相干，点任意一块下载原图 |
| 0x02 | 星座 | 占号未实现 | 暂按普通外观（规则待定） |

**外观在两处可选，互不干扰**：拆分卡顶部「密文外观」决定这次拆分写进密文的编号；
恢复卡「① 选择密文文件」右侧那组是**呈现方式**，默认听密文的，用户还能手动改
（外观只影响渲染，跟密码学无关，改哪套都不会解错文件）。换一份密文就回到"听密文的"。
日夜模式（亮/暗）是页面自己的主题，仍在页头卡片右上角，与外观这一层没有关系。

**普通模式可以「覆写」密文外观**（高级操作里第一项）。它把"怎么插入"和"恢复端看到什么"
这两件事拆开：插入仍走普通模式，任意文件、任意层数、假文件层、压缩与 OTS 全都照旧，
只有写进密文外层 `0x06` 的那个编号换成目标外观。用途是自己这边按最顺手的方式堆层，
收件人那边却拿到一块碎玻璃（或者反过来）。三个约定：

- 只影响 `0x06` 那个字节，**密码学上没有任何区别**，解出来的还是那些文件；
- 覆写成碎片的层数可以超过 6（普通模式不拦），第 7 层起不会出现在碎玻璃上，
  只在「文件信息与校验」里列出——拆分日志会提前警告；
- 切到「碎片」模式时这一项自动隐藏（那时界面本身就是碎片，覆写无从谈起），
  但之前选的值会记住，切回普通再拆分仍然生效。

碎片外观的约定与实现细节：

- **一块 = 一层 = 一个独立的文件**。拆分端只允许图片（按 `accept` + MIME/扩展名粗筛），层数上限 6；
  假层也占一块。「碎片」不是拼图：**形状共用、内容独立**——六块严丝合缝地拼满舞台（切线在
  `--poly` 里），但每块装的是自己那份密文，谁也拼不出整体。
- **k 就是格子的位置**：第 1 块要 1 片、第 2 块要 2 片……第 6 块要 6 片；n 正好等于文件数。
  于是**每多一片就多解开一个文件**：1 片开第 1 块，2 片连第 2 块一起开，凑齐 n 片全开。
  这条规矩是碎片外观的语义（普通模式仍是 3、4、5… 的递增链，随便改），
  `reclampFragmentShares()` 在切到碎片、以及层有任何增减时统一重排 k 与 n。
- **插入和恢复是同一块拼图**：拆分端选「碎片」后，层列表 / 大投放框 /「分给几个人」/ 假文件层 /
  高级操作全部收起，摆出来的就是恢复端那六块（`buildStage` + 同一份 `fragment.css`）。
  空格显示「+ 放图」，点一下或把图拖进来就塞满一块，标签上的 × 撤掉那一层。
  压缩固定 zstd L3、不提交 OTS——高级操作既然看不见，就真按默认值跑，不能偷偷沿用普通模式里勾过的联网选项。
- **恢复端按魔数判断"是不是图片"**（`styles.ts` 的 `sniffImageMime`），不信扩展名也不信内层 MIME：
  改了名的文本不该被画出来。不是图片的块退化成"文件块"——不画图，点一下下载。
- 六块的形状全写在 CSS（`.frag-slot[data-i=n]` 的 `--poly`，碎片本体 / 面子 / 光晕共用一份；
  `--bx/--by/--bw/--bh` 是同一个多边形的包围盒，也就是这张照片的取景框，**改 `--poly` 必须同步改它**；
  `--cx/--cy` 是这块碎片的"重心"，非图片块的内容和「+ 放图」摆在这儿——摆舞台中心会被切线切掉）。
  解锁前是暗玻璃 + 斜纹，解锁后是那块图。块数固定还有个好处：
  **不泄露真实层数**，暗着的块既可能是"还没凑够密钥"，也可能是"本来就没有内容"。
- **每张照片只对自己那块碎片的包围盒负责**（`--bx/--by/--bw/--bh`）：六块装的是六张**不同的**照片，
  像一趟旅行在六个地方拍的，内容有关联但从来不是同一张，所以谁也不该借用别人的取景框。
  `object-fit: cover` 让浏览器自己算缩放——大图缩小、小图放大，永远刚好盖住盒子，
  不用 JS 量 `naturalWidth`，也不会出现"1:1 大图只剩中间一小块"。
  `object-position` 用这块碎片的**重心**（`--cx/--cy`）：不规则四边形的视觉重点不在盒子正中央，
  把画面主体对过去，块里才有东西。`--os`（在 `.frag-stage` 上）是统一溢出量，1 = 恰好盖住，
  调到 1.05~1.12 会让照片多出一圈、被切线剪掉，像"照片边缘被剪"而不是"塞进相框"。
  `decoding="sync"`：异步解码会让碎块先空着几百毫秒，六块一起恢复时后半排明显是黑的。
- 标签是半透明胶囊（`backdrop-filter: blur`），**挂在舞台上而不是碎片里**——碎片带 `clip-path`，
  标签挂进去会被切线切掉半个字，位置单独写在 `.frag-tag[data-i=n]`。
  标签只写「编号 + 名字 + ×」：k 由位置决定，再写一行"需要几片"是把能推出来的信息重复贴在图上。
- 光晕是每块背后一片同形状的模糊亮片（`.frag-glow`，`blur` 与 `clip-path` 分在父子两层，
  否则模糊会被切回形状里），只从缝里透出来。
- **不做任何自动抠图**：主体边界完全由用户那张图决定（之前那套泛洪 + 焦点椭圆的启发式已整块删除）。
- **照片上不叠任何"边框"**：内描边、暗角、覆盖整面的白膜、`opacity < 1`——只要有一样，
  照片边上就会多出一圈灰。玻璃质感只留两层：极淡的颗粒（`soft-light` 0.12）和左上一道
  很淡的斜光（0.07）。悬停反馈也**不碰轮廓**：只让图片自己 `scale(1.02)` + 提亮 6%
  （它被裁在切线里，怎么动都碰不到断面）；描边类的亮边一律不用——`box-shadow` 从无到有无法过渡，
  鼠标进入的瞬间就是一条白边。整块碎片也不放大：那会把断面挪开，缝里那层磨砂光顺着亮起来，同样是一条白线。
- **背景是夜空**：舞台底下铺一层 `.frag-sky`——几团低饱和星云（蓝紫 / 深蓝 / 品红 / 青）、
  一道斜穿过去的银河带、60 颗星点（10 颗带光晕的亮星 + 50 颗小星，坐标写死，
  不然每次渲染都跳一次）。三颗亮星用 7.5s 的 `alternate` 缓慢呼吸，
  `prefers-reduced-motion` 下停掉并保持最亮那一档。全部是 CSS 渐变，没有一张图片：
  整页仍然自包含、零外发、可离线。
- **玻璃是半透明的深空玻璃**：碎片不填底色（填了就盖住夜空），面子是一层
  `rgba(22,29,54,.42)` 上深下浅的冷色玻璃，通透到能看见后面星星的明暗；
  颗粒压到 0.13（`screen`），只在玻璃上留一层质感，不糊住星点。
  非图片格保留颗粒 + 反光 + 断面高光；未解锁的格子是同一块玻璃、只是更暗，
  靠纹路（斜纹 / 交叉纹）区分「还差片」和「假层」，不靠颜色。
- **恢复界面由外观接管**：选中「碎片」，① 卡里就直接摆出那块碎玻璃。**这一步不等密文**——
  碎片是一整套界面而不是给密文配的皮肤，它的入口本来就通用（点格子 / 拖文件都走 `ingestFiles`，
  `.tscf` 与分片文本一起吃得下），所以选中就切过去，不必先对着「② 导入分片」等一份密文。
  有密文之后，密文投放框、「② 导入分片」整块（列表 / 输入框 / 从文件导入）和「恢复文件」
  按钮才一起收起（`.is-frag.has-ct`）；还没密文时投放框留着，它是当时唯一的密文入口，
  点空格子打开的文件框也不再限定类型。
  **点任意一块、点碎片之间的缝、或把文件拖进来**，都走同一个补片入口
  （`RestoreView.attachShare`）；补进来的片够 k 就自动开解，不用再按按钮。
  片够不够看的是最外层那块的 k（碎片外观恒为 1），所以第一片一到就开始解，
  之后每补一片都会再解一遍，多解开一个文件。点已解锁的块仍然是下载。
  默认外观不受影响，还是原来那套投放框 + 列表 + 按钮。
- **顺序随便挑**：①「选择密文文件」右边那组外观按钮**不依赖密文**，一开始就能点。
  选「碎片」是唯一会**立刻生效**的一档（界面已经摆出来了，六格标签写"空着"）；
  选默认外观则记为"待定"，第一份密文进来才认它（`restoreStyle()`：`overrideFor === null`
  表示待定）；之后再换一份密文则恢复成听密文的。自动开解的判定也覆盖了顺序——
  先放片、后放密文（外壳一进来才把界面切成碎片）同样会立刻开解，不必再补一片。
  恢复跑着的时候这组按钮跟着锁上，免得中途换外观把正在解锁的那份视图换掉。

代码上，**一个外观 = 一个模块**（`src/appearance/`）：

| 文件 | 职责 |
| --- | --- |
| `types.ts` | 三份契约：`SplitPolicy`（收什么文件、最多几层、文案）、`RestoreView`（lock / fake / unlock，可选 `attachShare` 接管补片入口）、`SplitView`（可选：外观自己的插入界面） |
| `plain.ts` | 默认外观：普通文件卡 |
| `fragment.ts` + `fragment.css` | 碎片：6 块拼满舞台的碎玻璃。`buildStage()` 是两端共用的骨架，`createFragmentView`（往外取图）与 `createFragmentSplitView`（往里塞图）只差喂进去的事件。图片取景（包围盒 + `object-fit: cover` + `--os`）全在 CSS，JS 不量尺寸 |
| `card.ts` | 两种外观共用的层卡、还差片行、假层行 |
| `index.ts` | 注册表：`splitPolicy(id)` / `createRestoreView(id)` / `createSplitView(id)`，未登记的编号落到默认外观 |

`main.ts` 不认识任何具体外观：收文件时问 `splitPolicy(id).accepts`，恢复时只把
「还差片 / 假层 / 解开一层」三个事件喂给 `RestoreView`。加新外观不改主流程，
只加文件 + 注册一行。

**密文侧（凑齐 k 片、解密并验签后才可见）——TSPK 载荷包**：

```
TSPK | v1
  0x01 FILENAME     utf-8   原文件名（可选；缺失时下载名用 YYYY-MM-DD.bin）
  0x04 CREATED_AT   8B      拆分时间（可选；缺失则用下载时刻，界面显示“时间未记录”）
  0x05 MIME         utf-8   原 MIME（可选）
  0x07 SHA256       32B     原始文件（解压后）的 SHA-256
  0x08 ALGO         1B      0x00..0x03，DATA 块的压缩算法（缺失 = 0x00）
  0x12 OTS_RECEIPT  ...     可选，OpenTimestamps 回执
  0x11 DATA         ...     原文件数据；ALGO≠0 时是压缩后的字节流
  0x13 NEXT         ...     可选，下一层的完整 TSCF 字节（末块）
```

### 压缩放在哪：压 DATA，不压整包

压缩只作用于 `0x11 DATA` 的值，TSPK 容器本身（magic/version/各 tag）保持明文可解析。这样：

| 问题 | 结论 |
|---|---|
| TSPK 还在吗 | 在。解密后第一件事仍是校验 `TSPK` magic + version，容器语义完整 |
| 算法编号够不够 | 1B = 256 个编号；将来要带参数（窗口/字典）时，TLV 的 len 字段天然支持多字节值，旧解析器按未知 tag 跳过 |
| 旧密文怎么办 | 没有 0x08 → 视为 0x00 → DATA 明文，逻辑与今天完全一致 |
| 完整性怎么算 | `0x07 SHA256` 始终是**解压后原文件**的哈希：先解压、再校验，OTS 锚定的也是同一个哈希 |
| 篡改 ALGO 会怎样 | 它在密文内、被 GCM 认证覆盖，改动即认证失败 |
| 为什么不压整包 | 压整包后解密结果是一段 zstd/gzip 流，TSPK magic 与 version 都不复存在，等于为了省几十字节把头丢掉 |
| 成本 | 每份密文多 6 字节（tag 1 + len 4 + 值 1），且只在密文里，不进入分片 |

| ALGO | 算法 | 定位 | 实测（24 文件 / 281.6 MB） |
|---|---|---|---|
| 0x00 | 不压缩 | 默认兜底；采样收益 <1% 时选它 | 已压缩格式（jpg/zip/mp4）压了等于白压 |
| 0x01 | zstd L3 | **默认** | 约 47% 压缩率，~97 MB/s |
| 0x02 | gzip 原生 | 兜底（CompressionStream，无额外依赖） | 34%，48 MB/s |
| 0x03 | zstd L19 | 极限档，显式选择 | 约 50%，2.5 MB/s，大文件会白等数十秒 |
| 0x04–0xFF | 预留 | 解析器遇到未知值报错，不猜测 | — |

拆分时的决策：对 DATA 前 256 KiB 采样试压，收益 <1% 直接写 0x00；否则按用户选项写 0x01–0x03。
内联 zstd WASM 后单文件产物为 **426 KB**（gzip 后 152 KB；wasm 246 KB 由 Vite 转成 data: URL 内联），仍然完全离线、零外部请求。
CSP 为此放开 `script-src 'wasm-unsafe-eval'`、`worker-src blob: data:` 与 `connect-src data: blob:`（仅本地，不外发）。

**分片 = 纯密钥材料**（保持最少存储）：`TSK1:x:组1,组2,…,组m`，组 = `k:y` 或裸 `y`

一个密文里可以套 m 层（每层一个真文件，或唯一一个假文件），每层有自己的 AES key 与阈值 k，
所有层共用同一套坐标，所以一片里带齐了 m 组 y。**每层独立决定要不要把 k 写进分片**
（层行上的「显示k」勾选）：写 k 的组是 `k:y`，没写的组是裸 `y`——恢复端从该层密文的
`0x02 K` 读，所以不写也能解开。混装合法，比如拆分端只给第 1 层和最后一层勾了显示：

```
TSK1:04829173:10000:y₁,y₂,y₃,y₄,20000,y₆…
└ 组1 k=10000  └ 组2-4 没写（参与者看到 "?"）  └ 组5 k=20000
```

这就是给活动参与者的视角：`1万 - ? - ? - ? - 2万`——起点终点可见，
中间各层要多少片只有解开上一层后（从密文里）才知道。

```
x      = 坐标（1..16 777 215），一片只写一次，十进制
         单层：紧凑写法，如 "7"（洗牌 1..n，最短 1 位）
         多层（或勾了「隐藏 n」）：定宽 8 位左补零，如 "04829173"（在 [1, 16 777 215] 内随机）
每组   = y（32 字节大端）的 base64，44 字符；带 k 时再加 ":k"
解析    = 组内按冒号切：1 段=裸 y，2 段=k:y，3 段以上=密钥损坏；
         k 不是 1..MAX 的整数、y 解不出 32 字节 → 一律报「密钥损坏」
整片   = 前缀 + 每组约 44 字符（带 k 时 +1~8），与 n 无关
```

x 提到前缀里是为了省空间：旧布局每组都要重复一份坐标，深链时这份重复会被放大几十倍，
而 x 本来就是一片一个值。

**多层为什么要把 x 定宽 + 随机**：若 x 仍按 `1..n` 洗牌，它的十进制位数就直接说明
"这套一共几个人"——1 位 → 不到 10 人，5 位 → 几万人。定宽 8 位 + 全域随机之后，
x 只剩"某个不超过 16 777 215 的数"，n 是多少完全看不出来。单层不需要这层伪装
（n 本来就写在密文的 `0x03` 里），所以保留最短写法。

域是 **secp256k1 基域 GF(2²⁵⁶ − 2³² − 977)**。选它的关键原因：`2²⁵⁶ − p = 2³² + 977 ≈ 4.3e9`，
所以任意 32 字节密钥落在域外的概率约 2⁻²²⁴（实测 2e6 次采样 0 命中），秘密可以原样当域元素用。
**绝不能对密钥做 `mod p` 归约**——那不是单射，两个相差 p 的密钥会塌成同一个域元素，
恢复只给出其中一个，另一个文件永久打不开。p 取 2²⁵⁵−19 就有 50% 的随机密钥需要归约，所以不选它。

万一真落在域外（2⁻²²⁴），`randomFieldBytes()` 直接**丢弃重取**新随机数，而不是取模。
所有会被当作秘密共享的 32 字节随机量（AES 密钥、多项式系数）都从这个函数出。

x 是公开坐标（单层 1..n 洗牌；多层在 [1, 16 777 215] 内随机并定宽），y = f(x) 是域元素。每片只自带各组的 k
（n 已从分片移除；单层密文把 n 写在 `0x03`，多层链完全不写）。同批片的组数、每组 k 必须完全一致，否则直接报错。

### 多层：靠内层的 0x13 NEXT 串起来

拆分从**最深层反向**做：先加密最深层，把它的整段 TSCF 字节放进上一层的 `0x13 NEXT`，
再加密上一层……最外层就是用户拿到的那个 `.tscf`。NEXT 是该层 **TSPK** 的最后一个块，
所以密文内层块序恒为 `FILENAME → CREATED_AT → SHA256 → MIME? → ALGO → OTS? → DATA → NEXT?`，
而明文外层恒为 `K → N? → IV → CIPHERTEXT`，无论链有多长都不变。

```
TSCF₁ ──密文解密后──> TSPK₁{ DATA₁ + 0x13 NEXT(TSCF₂) }
                          │
TSCF₂ ──密文解密后──> TSPK₂{ DATA₂ + 0x13 NEXT(TSCF₃) }
                          │
TSCF₃ ──密文解密后──> TSPK₃{ DATA₃ }        ← 没有 NEXT，链到底
```

- 凑够 3 片 → 解开 TSCF₁，拿到第 1 层文件；此时才看得到 TSCF₂ 的字节，但没有 4 片解不开
- 凑够 4 片 → 再解开 TSCF₂；依此类推
- 密钥材料足够时恢复是**逐层跑**的，每层一次插值（k 片）+ 一次 AES-GCM 解密
- 层数不进明文：只拿密文、没有密钥的人连"这套一共几层"都数不出来

**假文件**：只有一层，且必定是最后一层。它的字节结构与真文件完全一致
（FILENAME、CREATED_AT、和自己乱码对得上的 SHA256、ALGO），但拆分时
**分片共享的 `splitKey` 与加密用的 `key` 是两把不同的随机密钥**：

- 凑够 k 片 → 插值出来的是 `splitKey` → AES-GCM 认证失败 → 这一层永远解不开
- 它的 k 是唯一允许**大于 n** 的：设成 n+1 就连「凑够」都做不到
- 因此拿分片的人直到凑够那一层所需片数之前，都无法判断它是真文件还是假文件

对齐（32 / 256 / 自定义）只决定**一片里写几组 `k:y`**：真实层 + 假层之外补的都是
**诱饵组**——没有密文、只有随机 y，谁拿去插值都只会得到一串随机字节，与假层无法区分。
默认对齐 32 组，真实层已有 32 层就跳到 256，避免从组数反推真实文件数；
只有「自定义」被标为实验性。没加假文件层时不做任何补位，一片里就是真实层数。

复盘一下代价：诱饵组不带数据，所以密文大小只与真实层 + 那一层假文件有关（不是三十几倍）；
但每片长度会按对齐档位放大（32 组 ≈ 1.4 KB/片），n 很大时要留意分片文本体积。



**大 n 的代价**（实测，Node 22）：拆分是 `n × (k−1)` 次 256 位模乘，恢复是 `k²` 次。
k=10000 时单次多项式求值 3.23 ms，所以 n=100000 的拆分约 **331 秒**，k=10000 的恢复约 **65 秒**。
分片体积几乎不随 n 变：单层 n=100000 时每片约 45 字符，十万片合计 4.5 MB 文本。

因此 Shamir 运算全部跑在 **Web Worker** 里（`src/core/jobs.worker.ts`，用 `?worker&inline`
编译成 base64 blob，仍是单文件产物），主线程只负责进度条与日志，界面不会被算死。

拆分结果渲染也做了折叠：`n > 50` 时只渲染前 50 行，其余折叠成一行计数。
`n > 20` 时「下载全部」改为**打包一个 zip**（store 模式，`src/core/zip.ts`）——
浏览器会拦截连续几十上百次自动下载；条目数超过 65535 时写 ZIP64 EOCD，十万片也能一次下载。
恢复区也直接收这个 zip：按内容自动分流（`.tscf` → 密文、分片文本 → 逐片导入），
只遍历压缩包当前层级，当前层级只有 1 个文件夹时下钻一层（`readZip` 支持 store/deflate 与 ZIP64 条目数）。
分片不含任何元数据——OTS、签名、文件名都只活在密文里。

恢复时：k 片 combine → 32B key → 解开 TSCF → AES-GCM 认证失败即报
"分片/密文不匹配" → 解出 TSPK → SHA-256 校验 DATA → 原文件。
若内层含 OTS_RECEIPT：离线比对回执摘要与 DATA 哈希；可选在线完整验证（拉区块头对 merkle root）。

**OTS 的联网策略：只在白名单日历上查。** 2026-10-18 实测 OTS 公共池的几个日历
`POST /digest` 带 `Access-Control-Allow-Origin: *`（能提交），而 `GET /timestamp/<hex>`
一个 CORS 头都不带（读不到）。所以「自动查询升级状态」在浏览器里注定失败，
而且是一次白送的外发。现在 `ots.ts` 里有个 `CORS_CALENDARS` 白名单，
不在名单上的日历**一次请求都不发**，只在界面上静态说明"该日历不允许跨域读取，请下载 .ots 交给官方工具复核"。
白名单目前是空的——哪天某个日历补上 CORS 头，把 hostname 加进去就能启用。
这条也让"零外发"的隐私底线更硬：不勾 OTS 时，整个页面不会有任何网络请求。
