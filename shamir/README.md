# shamir — 点击即用的文件分片工具

> 任意文件进 → n 个分片 + 1 个密文出。凑齐任意 k 个分片 → 原文件回来。
> 纯前端、零后端、零外发请求。端点：https://tdstud1o.github.io/tool/shamir/
>
> 产物：密文 `<stem>.tscf`（TSCF 容器）+ 分片 `<stem>_shareN.txt`。
> **v0.2 破坏性更名**：容器头 SMCF/SMPK → **TSCF/TSPK**，扩展名 `.tsss` → **`.tscf`**；旧密文不再兼容（此前无外部用户）。

背景与生态位调研见博客：找遍了全网的 shamir 方案，没有我要的"点击即用"的版本（2026-10-17）。

## 验收标准

- 任意文件（照片/文档/存档/压缩包），不限格式
- 混合加密：随机 key 做 AES-256-GCM 加密文件；Shamir 只分片这个 key
- 返回物：n 个分片（每片几十字节文本）+ 1 个密文（压缩后通常远小于原文件）
- 恢复：任意 k 个分片 + 密文 → 原文件，校验失败明确报错
- 全程浏览器本地计算，GitHub Pages 静态部署

## 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 分片引擎 | **自实现 secp256k1 基域 GF(p) 上的 Shamir**（BigInt，零依赖） | p = 2²⁵⁶−2³²−977，32 字节密钥天然 < p，**不需要取模归约**（归约不是单射，会让两个密钥塌成同一个值）；x 不再被单字节坐标限制，n 上限 16,777,215；无查表、无运行时表 |
| 加密 | **Web Crypto API · AES-256-GCM** | 浏览器原生，无需引入库；key 32B 随机生成，IV 12B，AEAD 自带完整性 |
| 构建 | **Vite + TypeScript + vite-plugin-singlefile** | TS 类型安全；打包为**单个自包含 HTML**——可整页另存离线使用、可人工审计、无 CDN 运行时依赖 |
| UI | **无框架 vanilla TS + 手写 CSS** | 工具只有"拆分/恢复"两个动作，上框架是负资产；深色简洁风 |
| 分片载体 | 文本格式（带头校验），支持复制/下载/打印 | `TSK1:k:base64` 结构（TSK = TD Shamir Key，1 为格式版本），载荷 = `[32B y][x]`，几行字符，二维码/纸面均可承载 |
| 部署 | **GitHub Actions → actions/deploy-pages** | Pages 固定 URL 为 `tdstud1o.github.io/tool/`，Vite `base=/tool/shamir/` |

### 明确不选

- **React/Vue 等框架**：两个表单不需要组件体系，徒增体积与审计成本
- **运行时 CDN 引用**：隐私工具必须整页自包含，断网可用
- **后端 / 对象存储**：k-of-n 本来就只要求凑 k 片，云端存储反而扩大攻击面
- **SLIP-39/助记词生态**：本工具面向文件，不做 BIP39 兼容

## 数据格式（v1 草案）

两层同款 TLV 容器（PNG/age 风格，支持向前扩展）：

```
TLV 通用结构：magic(4B) + version(1B) + tag(1B) + len(4B 大端) + value 序列
兼容规则：解析器必须跳过未知 tag；约定 lastTag 的块必须放最后；单值上限 4 GiB
```

**内层 TSPK 载荷包**（先打包、再整体加密——元数据、存证、签名全部藏进密文）：

```
TSPK v1：
  0x01 FILENAME    utf-8 原文件名
  0x04 CREATED_AT  u64 毫秒（原文件创建/拆分时间，属于元数据，不外露）
  0x05 MIME        utf-8
  0x06 NOTE        utf-8 备注
  0x07 SHA256      原始 DATA 的 SHA-256（32B）
  0x12 OTS_RECEIPT OpenTimestamps .ots 回执原文（用户勾选才提交哈希）
  0x11 DATA        原始数据（最后一个块）
```

**明文侧（不凑齐分片也能看到的全部内容）——TSCF 密文容器**：

```
TSCF | v1
  0x02 K            1B   分片阈值（必需，与分片交叉校验）
  0x03 N            1B   分片总数（可选，缺失时以分片自带的 n 为准）
  0x04 IV           12B  AES-GCM nonce
  0x05 CIPHERTEXT   ...  AES-256-GCM(key, TSPK 包)，恒为末块
```

明文侧刻意只有「参数 + 12B 随机 IV + 密文」：没有文件名、没有大小提示、没有压缩算法。0x01（FILENAME）v1.2 起废止，旧文件解析时按未知 tag 跳过。

**密文侧（凑齐 k 片、解密并验签后才可见）——TSPK 载荷包**：

```
TSPK | v1
  0x01 FILENAME     utf-8   原文件名（可选；缺失时下载名用 YYYY-MM-DD.bin）
  0x04 CREATED_AT   8B      拆分时间（可选；缺失则用下载时刻，界面显示“时间未记录”）
  0x05 MIME         utf-8   原 MIME（可选）
  0x07 SHA256       32B     原始文件（解压后）的 SHA-256
  0x08 ALGO         1B      0x00..0x03，DATA 块的压缩算法（缺失 = 0x00）
  0x12 OTS_RECEIPT  ...     可选，OpenTimestamps 回执
  0x11 DATA         ...     原文件数据（末块）；ALGO≠0 时是压缩后的字节流
```

### 压缩放在哪：压 DATA，不压整包

压缩只作用于 `0x11 DATA` 的值，TSPK 容器本身（magic/version/各 tag）保持明文可解析。这样：

| 问题 | 结论 |
|---|---|
| TSPK 还在吗 | 在。解密后第一件事仍是校验 `TSPK` magic + version，容器语义完整 |
| 算法编号够不够 | 1B = 256 个编号；将来要带参数（窗口/字典）时，TLV 的 len 字段天然支持多字节值，旧解析器按未知 tag 跳过 |
| 旧密文怎么办 | 没有 0x08 → 视为 0x00 → DATA 明文，逻辑与今天完全一致 |
| 完整性怎么算 | `0x07 SHA256` 始终是**解压后原文件**的哈希：先解压、再校验，OTS 锚定的也是同一个哈希 |
| 篡改 ALGO 会怎样 | 它在密文内、被 GCM 认证覆盖，改动即认证失败 |
| 为什么不压整包 | 压整包后解密结果是一段 zstd/gzip 流，TSPK magic 与 version 都不复存在，等于为了省几十字节把头丢掉 |
| 成本 | 每份密文多 6 字节（tag 1 + len 4 + 值 1），且只在密文里，不进入分片 |

| ALGO | 算法 | 定位 | 实测（24 文件 / 281.6 MB） |
|---|---|---|---|
| 0x00 | 不压缩 | 默认兜底；采样收益 <1% 时选它 | 已压缩格式（jpg/zip/mp4）压了等于白压 |
| 0x01 | zstd L3 | **默认** | 约 47% 压缩率，~97 MB/s |
| 0x02 | gzip 原生 | 兜底（CompressionStream，无额外依赖） | 34%，48 MB/s |
| 0x03 | zstd L19 | 极限档，显式选择 | 约 50%，2.5 MB/s，大文件会白等数十秒 |
| 0x04–0xFF | 预留 | 解析器遇到未知值报错，不猜测 | — |

拆分时的决策：对 DATA 前 256 KiB 采样试压，收益 <1% 直接写 0x00；否则按用户选项写 0x01–0x03。
内联 zstd WASM 后单文件产物为 **400 KB**（gzip 后 142 KB；wasm 246 KB 由 Vite 转成 data: URL 内联），仍然完全离线、零外部请求。
CSP 为此放开 `script-src 'wasm-unsafe-eval'`、`worker-src blob: data:` 与 `connect-src data: blob:`（仅本地，不外发）。

**分片 = 纯密钥材料**（保持最少存储）：`TSK1:k:base64(payload)`，

```
payload = [y: 32 字节大端][x: w 字节大端]
定长在前、变长在后：y 恒 32 字节，x 的宽度 w = payload 长度 − 32，由 n 决定：
  n ≤ 255     → w=1，每片 33 B
  n ≤ 65 535  → w=2，每片 34 B
  n ≤ 16 777 215 → w=3，每片 35 B
```

域是 **secp256k1 基域 GF(2²⁵⁶ − 2³² − 977)**。选它的关键原因：`2²⁵⁶ − p = 2³² + 977 ≈ 4.3e9`，
所以任意 32 字节密钥落在域外的概率约 2⁻²²⁴（实测 2e6 次采样 0 命中），秘密可以原样当域元素用。
**绝不能对密钥做 `mod p` 归约**——那不是单射，两个相差 p 的密钥会塌成同一个域元素，
恢复只给出其中一个，另一个文件永久打不开。p 取 2²⁵⁵−19 就有 50% 的随机密钥需要归约，所以不选它。

万一真落在域外（2⁻²²⁴），`randomFieldBytes()` 直接**丢弃重取**新随机数，而不是取模。
所有会被当作秘密共享的 32 字节随机量（AES 密钥、多项式系数）都从这个函数出。

x 是公开坐标（1..n，洗牌后分配），y = f(x) 是域元素。n 的上限由坐标宽度决定，不再是 255。
每片只自带 k（n 已从分片移除，n 只存在于密文外层且可选），同批片 k 不一致立即报错。

**大 n 的代价**（实测，Node 22）：拆分是 `n × (k−1)` 次 256 位模乘，恢复是 `k²` 次。
k=10000 时单次多项式求值 3.23 ms，所以 n=100000 的拆分约 **331 秒**，k=10000 的恢复约 **65 秒**。
分片体积则几乎不变：n=100000 时每片 35 B，十万片合计 3.4 MB 载荷、5.7 MB 文本。

因此 Shamir 运算全部跑在 **Web Worker** 里（`src/core/jobs.worker.ts`，用 `?worker&inline`
编译成 base64 blob，仍是单文件产物），主线程只负责进度条与日志，界面不会被算死。

拆分结果渲染也做了折叠：`n > 50` 时只渲染前 50 行，其余折叠成一行计数。
`n > 20` 时「下载全部」改为**打包一个 zip**（store 模式，`src/core/zip.ts`）——
浏览器会拦截连续几十上百次自动下载；条目数超过 65535 时写 ZIP64 EOCD，十万片也能一次下载。
分片不含任何元数据——OTS、签名、文件名都只活在密文里。

恢复时：k 片 combine → 32B key → 解开 TSCF → AES-GCM 认证失败即报
"分片/密文不匹配" → 解出 TSPK → SHA-256 校验 DATA → 原文件。
若内层含 OTS_RECEIPT：离线比对回执摘要与 DATA 哈希；可选在线完整验证（拉区块头对 merkle root）。
